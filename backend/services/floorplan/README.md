# Сервіс «макет квартири»: план приміщення → друкована 3D-модель

Користувач вантажить план (фото креслення, скан БТІ, PDF забудовника, скріншот),
перевіряє розпізнані стіни й масштаб — і отримує водонепроникний 3MF/STL/GLB
макета своєї квартири.

## Пайплайн

```
файл → preprocess → детекція → vectorize → [РЕДАКТОР КОРИСТУВАЧА] → builder → 3MF
        ↑ dewarp,    ↑ NN або    ↑ маска →                          ↑ буфер стін,
          освітлення,  класичний   відрізки                           2D-виріз дверей,
          нахил        CV          + товщини                          3D-виріз вікон
```

| Модуль | Роль |
|---|---|
| `plan_model.py` | `PlanVector` — спільний контракт: стіни (центральні лінії + товщина), отвори, кімнати |
| `preprocess.py` | PDF/фото → вирівняний растр; перспектива, освітлення, нахил |
| `detect_nn.py` | ONNX-сегментація (стіна/двері/вікно). Немає ваг → повертає `None` |
| `detect_cv.py` | Класична детекція без нейромережі: товстий штрих або штрихований/порожній стиль |
| `vectorize.py` | Маска → відрізки стін, товщини, отвори |
| `scale.py` | м/піксель: лінійка користувача, OCR розмірів, PDF-вектор, ширина дверей |
| `builder.py` | `PlanVector` → друкований меш (мм) |
| `pipeline.py` | `analyze()` та `build()` — те, що викликає `main.py` |

## Головні рішення (і чому саме так)

**Стіни — це центральні лінії + товщина, а не контури.** Тільки так `shapely.buffer`
дає правильні стики на перехрестях, і тільки так стіну можна тягати в редакторі.

**Масштаб підтверджує людина.** Помилка масштабу не видно на екрані — вона
виявляється, коли надрукований виріб уже поїхав до клієнта. Автоматика лише
пропонує значення разом із джерелом і впевненістю.

**Двері ріжуться у 2D, вікна — у 3D.** Двері йдуть від підлоги, тож це просто
віднімання полігонів. Один 3D-boolean (manifold3d) лишається тільки на вікна.
Менше булевих операцій — менше шансів отримати негерметичний меш.

**Підошву замикають морфологією, з радіусом у МЕТРАХ.** Вхідні двері, балконний
блок і панорамне вікно розривають зовнішній контур квартири. Об'єднання стін
розсипається, «залити дірки» вже нічого не дає — і основа вироджувалась у
прямокутну плиту: квартира на підносі. Заміряно на реальних планах: 40 випадків
із 87. `builder._close_footprint` зшиває розрив розширенням і стисканням назад
(стіни при цьому не рухаються, змінюється лише основа), пробуючи ширини прорізу
1.0 → 1.6 → 2.2 → 3.0 м. ПАСТКА: перша версія брала радіус від ТОВЩИНИ СТІНИ
(≈0.15 м) — розриви лишались незшитими, підошва виходила у формі самих стін:
одна деталь, але кімнати без підлоги, тобто ГІРШЕ за плиту. Критерій успіху не
«один полігон», а «підошва накрила ≥0.6 габариту».

**Висота стін макетна (22 мм), а не в масштабі.** Заміри слайсером: 8 мм → 4 год
друку, 45 мм → 8.4 год, при тому що товщина стіни 1.2→2.0 мм додає лише 3%.
Низькі стіни ще й краще показують планування згори. Справжня висота — опція.

**Мінімальна товщина стіни 1.2 мм** (3 периметри соплом 0.4). Тонше слайсер
викидає стіну МОВЧКИ — на друку її просто не буде.

**Три джерела навчальних даних, усі комерційно чисті.** CubiCasa5K (найкращий
за якістю) — CC BY-NC, тобто некомерційний, а monadruk продає друк: відпадає.
Тому власний генератор (`synth.py`) + реальна геометрія Swiss Dwellings +
реальні зображення Floor Plan CIS. Деталі нижче.

**PDF через pypdfium2 (BSD) + pdfplumber (MIT).** PyMuPDF/`fitz` — AGPL-3.0:
його використання в мережевому сервісі зобов'язує відкрити весь бекенд. Є тест,
який стежить, щоб він не повернувся (`test_no_agpl_pdf_dependency`).

## Дані для навчання

Три джерела, усі з ліцензією, що дозволяє КОМЕРЦІЙНЕ використання:

| Джерело | Ліцензія | Роль | Модуль |
|---|---|---|---|
| власний генератор (BSP) | наше | необмежений обсяг, повний контроль стилів | `synth.py` |
| **Swiss Dwellings v3** (6000 квартир) | CC BY 4.0 | справжня ТОПОЛОГІЯ: еркери, скоси, ніші | `datasets.py` + `geom_render.py` |
| **Floor Plan CIS** (372 навч.) | CC BY 4.0 | справжні ЗОБРАЖЕННЯ нашого домену | `fpc.py` |

⛔ CubiCasa5K, RPLAN, Structured3D, ZInD — CC BY-NC / research-only. Не
використовуються: ваги, навчені на них, це похідна робота, а сервіс платний.

Підготовка (один раз):
```bash
# Swiss Dwellings → 6000 планувань у кеш
python -m ml.floorplan.datasets build --limit 6000
# Floor Plan CIS → npz-пари для тренування
python -m ml.floorplan.fpc export --split train
# перевірка на реальних планах
python -m ml.floorplan.fpc eval --split valid
```

## Нейромережа

Тренування (лише локально, потрібна GPU):

```bash
python -m ml.floorplan.train --steps 12000 --batch 2 --size 512 --workers 3
python -m ml.floorplan.export_onnx --ckpt ml/floorplan/_checkpoints/floorplan_seg_best.pt
```

Ваги кладуться у `backend/models/floorplan_seg.onnx` (або шлях у `FLOORPLAN_ONNX`).
Файл **не в git** — вантажиться на сервер окремо. Немає файлу → сервіс автоматично
працює класичним CV, і це нормальний робочий режим, а не помилка.

⚠️ **Пастка fp16.** На GTX 1650 (sm_75) з cuDNN 9.1 згортки у fp16 при `batch≥3`
мовчки повертають NaN — вхід скінченний, вихід NaN, помилки немає. `train.py`
перевіряє це на старті (`amp_is_safe`) і сам перемикається на fp32. Перевірка
робиться в `eval()`-режимі: у `train()` NaN осів би у running-статистиках
BatchNorm, і модель тренувалась би нормально, але в eval видавала самі NaN.

## API

| Ендпоінт | Що робить |
|---|---|
| `POST /api/floorplan/analyze` | data-URL файлу → план у пікселях + масштаб + превʼю |
| `POST /api/floorplan/generate` | підтверджений план → задача (далі `/api/status`, `/api/download`) |
| `GET /api/floorplan/capabilities` | чи є нейромережа/OCR/PDF на цьому сервері |

Файл іде base64-рядком у JSON (у цьому бекенді немає жодного `UploadFile`, а
Caddy проксіює лише `/api/*` з лімітом тіла 50 МБ). Плани користувачів **не
зберігаються** на диску: превʼю повертається в тілі відповіді.

## Прод-обмеження (4 ГБ VPS)

- Вхід обрізається до 2400 px.
- `onnxruntime` — 1-2 потоки (`FLOORPLAN_ONNX_THREADS`).
- Генерація проходить через `gen_queue` разом із мапами: дві важкі задачі
  одночасно на цій машині = OOM.
- `torch` на сервер НЕ ставиться взагалі.

## Заміряна якість на РЕАЛЬНИХ планах

Датасет **Floor Plan CIS** (500 планів з оголошень нерухомості РФ/СНД, ручна
розмітка стін, CC BY 4.0). Це єдина чесна перевірка: усе інше ми малюємо самі.

| Модель | IoU стін | precision | recall | наскрізно |
|---|---|---|---|---|
| лише власна синтетика | 0.508 | 0.600 | 0.769 | — |
| + реальна геометрія (Swiss) | 0.529 | 0.606 | 0.808 | — |
| **+ реальні CIS + маркетинговий стиль** | **0.640** | 0.671 | **0.933** | **87/99 (88%)** |

По зображеннях: медіана IoU **0.848**, у 78% планів IoU > 0.7. Held-out test
(29 планів, ніколи не бачених): IoU стін 0.586, recall 0.827.

**Повнота** (чи замикаються кімнати) на реальних планах: **79%**, при стелі 97%
(стільки дає той самий векторизатор з ІДЕАЛЬНОЇ ручної маски). Тобто вузьке
місце — маска мережі, а не геометрія.

Усі 87 планів, що пройшли, дали **герметичний односкладовий** меш (41 г PLA,
1.3 с). Відмови: 8 — автоматичний масштаб (виправляє користувач лінійкою або
площею), 3 — надто мале зображення, 1 — надто гострий кут зйомки. Тобто сервіс
НЕ видає брак мовчки: він або робить коректну модель, або відмовляється з
поясненням.

**Форма основи** (заміряно на тих самих 87 планах):

| | було | стало |
|---|---|---|
| прямокутна плита замість обрису квартири | 40/87 (46%) | **6/87 (7%)** |
| площа підошви / габарит (медіана) | 1.00 | **0.66** |

**Масштаб «загальна площа з договору»** — там же:

| | було | стало |
|---|---|---|
| площа приміщень не рахується взагалі | 36% планів | **0%** |
| площа приміщень / габарит (медіана) | 0.08 | **0.80** |
| похибка масштабу на геометрії Swiss (медіана / 90-й перц.) | 8.5% / 46.9% | **7.4% / 39.5%** |

⚠️ Компроміс задокументовано: адаптація до реальних планів коштувала IoU підошви
на синтетиці (0.756 → 0.696), але замкнених кімнат стало БІЛЬШЕ (114 → 121 зі
126) — бо разом із нею полагодили оцінку тла в preprocess. Користувачі вантажать
реальні плани, не наші рендери, тож обмін вигідний у будь-якому разі.

## Заміряна якість на синтетиці

Вибірка: 40-60 синтетичних планів **усіх стилів** (залиті / штриховані /
контурні стіни, різні відтінки, осі з кружечками, штампи, меблі, підписи).
Раніші заміри робились на ОДНОМУ стилі й давали завищену картину — не
повторювати цю помилку.

| Показник | Класичний CV | Нейромережа |
|---|---|---|
| IoU підошви стін | 0.06 | **0.74** |
| знайдено справжніх стін (по довжині) | — | **84%** |
| знайдене, що справді стіна | — | **85%** |
| замкнених кімнат | ~1% | **279/289 (97%)** |
| двері / вікна | — | **98% / 99%** |
| герметичний односкладовий меш | 15/19 | **40/40** |
| точність габариту виробу | ≤0.01 мм | ≤0.01 мм |
| час аналізу (аркуш 950-2400 px) | ~7 с | **0.8-2.2 с** |

Точність масштабу за способом задання: лінійка користувача — точно за
визначенням; OCR розмірів — 1.6%; **загальна площа з договору — 2.2%**;
ширина дверей — ~15% (лише як підказка, не для генерації).

⚠️ Усі цифри — на СИНТЕТИЦІ, на якій мережа й навчалась, тобто оптимістичні.
На реальних БТІ-планах сервіс не валідовано жодного разу.

### Що вже перевірено і ВІДКИНУТО (не переоткривати)

| Ідея | Замір | Чому відкинуто |
|---|---|---|
| міряти товщину стіни профілем чорнила | 7 px → 11 px при еталоні 5.6 | distance transform у векторизаторі точніший (3-5%) |
| дорощувати маску мережі в замкнене чорнило | кімнат 88/126 проти 92/126 | гірше; корінь був у нереалістичній синтетиці |
| уточнювати межі стін перетином із чорнилом | кімнат 92/126 проти **121/126** | рвало стіни на блідих лініях |
| euler_number == 2−2·(кількість кімнат) | 15/15 хибних тривог | у «лотка» з основою це не виводиться з кількості кімнат |
| інференс на рідній роздільності (960 px) | recall 0.98 → 0.86 | модель навчена на 512-640, стіни стають надто товстими |
| площа приміщень через заливку дірок | 0.08 габариту замість ≈0.8 | один розрив у зовнішній стіні — і контур просочується крізь щілину |
| те саме через зовнішній контур компоненти | так само 0.08 | той самий розрив, та сама причина |
| увігнута оболонка (`shapely.concave_hull`) | ratio 0.4 → похибка 30%, ratio 0.25 → 93%; **СЕГФОЛТ** на частині планів | опукла і точніша, і не падає |
| радіус замикання підошви від товщини стіни | підошва у формі стін, кімнати без підлоги | проріз ≈ метри, товщина ≈ 0.15 м — різниця на порядок |

## Тести

```bash
python -m pytest tests/test_floorplan.py -q
```

Найважливіші інваріанти: габарит виробу дорівнює замовленому, меш герметичний і
односкладовий, стіни не тонші за сопло, розміри плану відновлюються з точністю
до 1%, сервіс працює без нейромережі.
